                   -- CHECK (stock_qty >= 0)

                   -- colour is nullable: a product with no colour gallery gets one

                   session_token (unique), updated_at
                   -- UNIQUE(user_id) with NULLs distinct in Postgres: one cart per
                   --  account, unlimited guest carts

cart_items         id, cart_id → carts CASCADE, variant_id → product_variants CASCADE, qty
                   -- UNIQUE (cart_id, variant_id), CHECK (qty > 0)

                   status (order_status), subtotal, shipping_fee, total (all numeric(10,2)),
                   ship_to_name, ship_to_address, ship_to_city, ship_to_phone, ship_to_email,
                   placed_at

                   product_name, size, colour, unit_price numeric(10,2), qty
                   -- name, size, colour and price snapshotted at time of sale

                   status (payment_status: pending|paid|failed|cancelled),
                   amount numeric(10,2), reference, created_at

                   courier, status (shipment_status), created_at

                   user_id → users SET NULL (nullable), order_id → orders SET NULL (nullable),

### Design notes worth defending to a panel

The original four, all still true:

- `order_items` snapshots product name and price. A later price change must never alter
  historical orders.
- `product_variants` with `UNIQUE (product_id, size, colour)` is what makes per-size stock
  possible. Everything about inventory depends on this table.
- `products.slug` is stored and permanent, so renaming a product does not break its URL.
- Shipping address on `orders` is copied, not referenced — she may edit or delete an address later.

Added during Phase 1:

- **Money is `numeric(10,2)`, never float.** Binary floating point cannot represent ₱662.10
  exactly, so totals drift by fractions of a centavo and eventually disagree with the sum of
  their line items. `numeric` stores decimal digits and arithmetic on it is exact. Postgres also
  has a `money` type; it was deliberately not used because its formatting depends on the
  server locale setting.
- **Timestamps are `timestamptz`, defaulting to `now()`.** It stores an absolute instant, so a
  row written by a server running in UTC still reads correctly in Manila. Plain `timestamp`
  throws that information away and the offset can never be recovered.
- **Primary keys are `integer GENERATED ALWAYS AS IDENTITY`, not UUIDs.** Identity is the
  SQL-standard way to say "the database assigns this", and `ALWAYS` means an application bug
  cannot write its own primary key by accident. Small, ordered, readable in a URL, and easy to
  explain out loud.
- **Enums are Postgres enums, which are one-way doors.** `ALTER TYPE ... ADD VALUE` works but a
  value can never be removed. `order_status` and `shipment_status` are the two most likely to
  grow; if either needs to be freely editable, convert it to a lookup table before Phase 4.
- **`CHECK (stock_qty >= 0)` is a real constraint here, not decoration.** MySQL parsed and
  silently ignored `CHECK` until 8.0.16. Postgres enforces it, which is why it can serve as the
  backstop for task 3.7.
- **Concurrency is handled by a conditional UPDATE, not by a transaction.** The Neon HTTP driver
  has no interactive transactions, so the classic read-stock-then-write-stock pattern is not
  available. Instead:

  ```sql
  UPDATE product_variants
     SET stock_qty = stock_qty - $1
   WHERE id = $2 AND stock_qty >= $1
  ```

  The `WHERE` test and the decrement evaluate atomically inside the single statement, so two
  simultaneous buyers of the last XL cannot both succeed. Check the affected row count: 1 means
  the stock was taken, 0 means someone else got there first and the order must fail cleanly.
  This is a better answer for the panel than "we wrapped it in a transaction", because it
  explains *why* it is safe.
- **A card never loads variant rows.** Sold-out on a listing page is a `NOT EXISTS` aggregate
  folded into the same statement that fetches the product, so a category page costs 2 queries
  regardless of catalogue size rather than 1 + N.

### Before you start Phase 2 — how /admin is secured today

`middleware.ts` returns a bare **404** for `/admin` and everything under it unless the
environment variable `ADMIN_ENABLED` is exactly `true`. It is set nowhere — not in
`.env.example`, not in `.env.local`, not in Vercel — so admin is dark on the staging URL and in
production. To work on admin styling locally, run `ADMIN_ENABLED=true npm run dev`.

That is a shutter, not a lock. It has no concept of a user, and anyone who can set an
environment variable on the deployment can open the whole thing. **Task 2.1 replaces it with
real authentication**, at which point the `ADMIN_ENABLED` check should be deleted rather than
kept alongside — two overlapping gates is how one of them ends up accidentally disabled.

Also note the three admin write actions in `app/actions.ts` — `addProduct`, `updateProduct`,
`deleteProduct` — currently **throw** a "not implemented until Phase 2" error. They were written
against the old flat `products` table with `image`, `colors` and a string `category` column,
none of which exist. Tasks 2.3 to 2.7 rewrite them against the normalised schema. Do not try to
revive the old versions.

Task 2.5 also absorbs the **upload half of task 1.11**: `scripts/migrate-images.ts` already
proves the Cloudinary path end to end, so 2.5 is a UI and a server action over the same API,
not new infrastructure. One thing it must get right — Cloudinary delivery URLs carry a version
segment (`/v1788342689/`), so replacing a photo means writing the **new** `secure_url` back to
`product_images.url`. Overwriting the asset alone leaves the old version live.

### Before you start Phase 3 — the driver constraint that shapes task 3.7

**The Neon HTTP driver has no interactive transactions.** `db.transaction()` throws
`No transactions support in neon-http driver`. This is not a bug to route around later; it
determines how 3.7 is written.

**Stock deduction: conditional UPDATE, one statement.**

```sql
UPDATE product_variants
   SET stock_qty = stock_qty - $1
 WHERE id = $2 AND stock_qty >= $1
```

The test and the decrement evaluate atomically within the statement, so the last XL cannot be
sold twice. Branch on the affected row count: 1 means the stock was taken, 0 means another
buyer won and the order must fail cleanly with a message naming the item. `CHECK (stock_qty >= 0)`
sits underneath as a backstop — if it ever fires, the deduction logic is wrong and the write
aborts rather than recording negative stock.

**Multi-table order write: `db.batch([...])`.** Neon executes a batch as a single server-side
transaction, so `orders` + `order_items` + `payments` land together or not at all. The catch is
that a batch is non-interactive — every statement is sent at once and you cannot branch on an
intermediate result. So the order of operations is:

1. Deduct stock with the conditional UPDATE, one statement per line item. Stop on the first
   failure and report which item sold out.
2. Insert the `orders` row with `RETURNING id`.
3. `db.batch()` the `order_items`, `payments` and any `shipments` rows using that id.

Step 1 is not atomic with steps 2 and 3. If step 2 fails after stock was taken, that stock is
held by nothing. Decide before writing 3.7 whether to compensate by adding it back, or to accept
the gap for a demonstration-mode shop and log it. Say which in the handover — the panel may ask.

**If full atomicity is required**, the alternative is the `neon-serverless` WebSocket `Pool`
driver, which does support interactive transactions. Node 24 has a global `WebSocket`, so it
needs no extra dependency. That is a deliberate driver swap in `lib/db.ts`, not a code tweak,
and it reintroduces connection handling — weigh it against the shop being demonstration mode.

## Sequencing rules

- **Schema before code.** Lock it in Phase 1 and change it only deliberately. Schema churn is the
  most expensive rework there is.
- **Deploy early.** Staging URL from week 1 kills "works on my machine" while it is still cheap.
- **Weekly demos, always.** A 2-minute screen recording each Friday is the best protection against
  "this isn't what I wanted" in week 5.
- **Deferred features are change requests.** Quote separately, agree in writing, never absorb.
